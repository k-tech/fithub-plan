# 手工测试指南

功能已实现但**尚未由你实测**。这份清单按"一个人能照着点完"来写，覆盖产品规格
（`01`–`06`）里的能力。每条都给了预期结果，不符合就是缺陷。

- 环境准备见 `README.md` 的 **Run locally**。两个终端：一个跑后端（8080），一个跑
  前端（5173）。浏览器开 <http://127.0.0.1:5173/>。
- 本地登录用页面上的"本地开发账号"选择器。`admin@fithub.local` 是管理员，用它建团队。
- 建议准备两个非管理员账号（如 `alice@fithub.local`、`bob@fithub.local`），很多规则
  需要"两个人"才测得出来（不能自己批准自己、权限被撤掉等）。
- 勾选框的意思是"我实际做过并确认符合预期"。

## 1. 账号、团队与加入申请

- [ ] 用 `admin@fithub.local` 登录，创建一个团队（例如"工程团队" / `engineering`）。
- [ ] 切到员工账号，在"团队"页提交加入申请。
- [ ] 切回管理员，在管理控制台看到待审申请，点批准。
- [ ] 员工账号能看到该团队，未批准的账号看不到。

预期：未获批准的员工没有团队资格，也就无法访问该团队的内部仓库。

## 2. 仓库与可见性

- [ ] 员工创建仓库（可选"授予所属团队写权限"）。
- [ ] 检查三种可见性的差别：`公开` 匿名可见、`内部` 仅团队成员、`私有` 仅被授权者。
- [ ] 用未授权账号访问内部仓库地址。

预期：内部/私有仓库对无权限者返回**找不到**，而不是"无权限"——不能泄露仓库存在。

## 3. Git 传输

- [ ] 克隆、拉取、推送（HTTPS + 访问令牌），再直接更新默认分支。
- [ ] 用同一个令牌，在**权限被撤掉之后**再推一次。

预期：克隆/拉取/推送正常；撤权后的下一次推送被拒绝，不需要等令牌过期。

## 4. 文件浏览与历史

- [ ] 浏览目录、文件内容、README 预览。
- [ ] 看提交历史与单个提交的详情（改了哪些文件、增删行数）。

## 5. Issue

- [ ] 创建 Issue，评论，关闭，重新打开。
- [ ] 建标签（名称 + 颜色 + 说明），打到 Issue 上，按标签筛选。
- [ ] 指派给一个有仓库读权限的人，按指派人筛选。
- [ ] 建里程碑，挂到 Issue 上，按里程碑筛选。
- [ ] 在 PR 描述里写 `Fixes #<Issue 号>`，然后合并该 PR。

预期：筛选生效；合并成功后，被 `Fixes` 引用的 Issue **自动关闭**。
Issue 和 PR 共用同一套编号，不会出现两个 #7。

## 6. 拉取请求与行内评论

- [ ] 从开发分支向 `main` 提 PR。
- [ ] 在 diff 的某一行留行内评论，并回复成一条对话。
- [ ] 让另一个人留下批准意见；尝试自己批准自己的 PR。

预期：**自己不能批准自己**；其他写入者可以留下审查意见，但审查是自愿的，不是合并条件。
- [ ] 批准后，往分支上再推一个提交，再看那条行内评论。

预期：原评论被标为"基于旧版本"，**而不是**悄悄移到某个新行上。

## 7. PR 合并

- [ ] 创建一个不需要 CI 的普通 PR，不提交任何审查意见，直接用写入权限合并。
- [ ] 再直接推送到默认分支，确认更新成功。

预期：写入权限足够直接推送或合并；审查和 CI 都不作为阻拦条件。

## 8. 权限被撤的实时生效（重点）

- [ ] 让同事在你的仓库里当协作者（写权限），他确认能推。
- [ ] 你在设置里把他的权限撤掉，让他**不重新登录**再推一次。

预期：立刻被拒绝。这一条是专门针对"长连接 Git 进程里权限检查被绕过"设计的。

## 9. 自动检查（CI）

准备：仓库的 `main` 上放一个 `.fithub/workflows/verify.yml`（写法参考
`README.md` 的 **Running CI** 一节），并启动一台执行机。

- [ ] 往分支推代码，观察仓库的"自动检查"页出现新的运行。
- [ ] 点进去看每个子任务的状态和输出日志。
- [ ] 让某个子任务失败（例如让它 `exit 1`），查看失败状态和日志。
- [ ] 即使检查失败，仍可由写入者直接更新分支或合并一个可合并的 PR。

预期：CI 正常报告通过或失败，但结果不会阻止推送或合并。

- [ ] 用手动触发功能跑一次。
- [ ] 取消一个正在跑的运行。

### SSH 自动部署（演示版）

准备一台可临时发布的测试服务器，并使用专用测试 SSH 密钥；runner 镜像需要 `ssh` 客户端。先在仓库 **设置 → SSH 部署** 保存私钥，再在默认分支工作流里加一个 `needs: [test]`、`secret-refs: [DEPLOY_SSH_KEY]` 的部署任务。

- [ ] 往默认分支推送一次，等检查任务成功后确认部署任务运行并连接服务器。
- [ ] 往非默认分支推送，确认该分支任务拿不到部署密钥。
- [ ] 删除密钥后再次触发，确认 SSH 发布不能成功。

预期：仅显式引用密钥且等待检查通过的默认分支部署任务会联网；普通检查任务仍不能联网。只使用临时演示凭据，密钥目前明文存储，不要使用生产服务器或生产密钥。

## 10. 权限越界（重点）

- [ ] 用一个只有读权限的账号，尝试改动 `.fithub/workflows/` 下的文件并推送。

预期：被拒绝。**流水线定义只能由仓库管理员改**，否则提 PR 的人就能改掉管自己的规则。

- [ ] 确认工作流定义取自 `main`，而不是被推送的那个分支：在一个分支上改坏流水线，
  推上去看它是否影响该分支的检查。

预期：不影响——检查仍按 `main` 上的定义跑。

## 11. 站内通知

- [ ] A 创建 Issue，B 在下面评论、并把 A 指派进去；看 A 的收件箱。

预期：A 收到 **2 条**（评论 + 指派）；**B 自己收到 0 条**（自己做的操作不通知自己）。

- [ ] B 在 A 的 PR 上留一条行内评论。
- [ ] 让检查失败一次。
- [ ] 顶部铃铛上的数字，与你点进去看到的未读条数。

预期：一致。铃铛上的数字不会比列表里实际能看到的更多。

- [ ] 在"未读"里把一条标为已读；再用"全部标为已读"。
- [ ] **撤掉 A 对某仓库的权限**，让 A 刷新收件箱。

预期：关于该仓库的通知**从列表和未读数字里一起消失**（数据没被删）。
- [ ] 把权限**加回来**，再让 A 看收件箱。

预期：通知回来了，而且**原来没读过的还是未读**（不是被悄悄消费掉）。

## 12. 命令行与 AI 助手

- [ ] `fh run list` / `fh run view` / `fh run logs`（可加 `--job`、`--after` 续读）。
- [ ] `fh notify list` / `fh notify list --unread` / `fh notify read`。
- [ ] 接上 AI 助手（`fh mcp`），让它查一下某个版本有没有通过检查。

预期：命令行与网页看到的是同一份数据；日志中断后能用游标续读，不重复不遗漏。

## 13. SSH 接入（需真实环境）

- [ ] 上传 SSH 公钥，用 `ssh://git@<主机>/<团队>/<仓库>.git` 克隆。

预期：能克隆；**不能执行任意命令**（网关只允许 Git 的收发包）。
这一项需要真机 sshd，是本清单里唯一必须由你准备环境的部分。

## 已知不做的部分（不是缺陷）

- 密集的多人协作、超大仓库性能压测没有做过。
- 流水线目前只支持一个演示用 SSH 密钥引用 `DEPLOY_SSH_KEY`；产物下载、部署审批、矩阵任务、复用工作流、`${{ }}` 表达式、第三方 Action 仍不支持。这些是**故意**拒绝而不是"接受了但行为不同"。

## 反馈方式

发现不符合预期时，记下：**在哪一页、点了什么、看到什么、期望什么**。
如果有服务端日志（后端终端）或浏览器控制台的报错，一并给我，能省很多定位时间。
